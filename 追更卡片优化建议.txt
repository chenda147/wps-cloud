追更卡片优化建议（参考 Sonarr / Prowlarr / Jellyseerr / Bazarr 等成熟追更类项目）
================================================================================
基于 github 上成熟的 PVR/追剧自动化项目（Sonarr、Prowlarr、Jellyseerr、Bazarr）
在「追更/监控卡片」上的通用做法，结合本项目当前 admin_settings.html 追更卡片实现，
整理出以下 7 条可落地优化。前几条为纯前端、改动小、收益高。

--------------------------------------------------------------------------------
★1. 进度条 + 缺失集高亮（Sonarr 核心做法）
--------------------------------------------------------------------------------
现状：
    卡片文字 "S01 · 起始 0 集 · 已追至 10 集 · 已上传 237 集"
问题：看不出「还差多少没追到」，缺失集淹没在文字里。
优化：
    - 卡片内加一条细进度条：已上传集数 / 当前已知最高集数 的比例填充。
    - 缺失集以红色小圆点/文字行展示，如 "缺: 11,12,18"。
    - 数据可用现有字段推导：期望集 = base_ep..progress_ep，缺失 = 期望集 - done_eps。
收益：一眼看清追更进度与缺口。  改动量：小。

--------------------------------------------------------------------------------
★2. 区分「已下载 / 已上传 / 缺失」三态（Sonarr downloaded/imported/missing）
--------------------------------------------------------------------------------
现状：
    done_eps 同时承担「下完」和「上传完」，用户无法判断卡在下载还是上传。
优化：
    - 卡片显示三态徽章：已下 X / 已传 Y / 缺 Z。
    - 后端在检查时分别记录 downloaded_eps 与 done_eps(已上传)；前端分别展示。
    - 若暂不改后端，可在前端用「已传 Y」与「缺失 Z」对比推断卡点。
收益：精确定位是卡在下载还是上传。  改动量：中（后端需补 downloaded_eps）。

--------------------------------------------------------------------------------
★3. 状态机术语收敛，去掉误导性的「运行中」（Sonarr Monitored/Paused/Ended）
--------------------------------------------------------------------------------
现状：
    只要 enabled 即显示「运行中」，但追更是定时/事件触发，平时是「监控中」。
优化：
    状态四态：
        监控中（绿，脉冲）—— 启用且未在跑任务
        已停止（灰）—— stopped=true
        已停用（黄）—— enabled=false
        出错（红，脉冲）—— warn_level=error 且有 active 任务
    「运行中」只在真有 active 任务时出现。
收益：不再误导用户以为一直占用资源。  改动量：小。

--------------------------------------------------------------------------------
★4. 失败卡片可「一键重试」（Sonarr 出错条目上的 Search/Retry 按钮）
--------------------------------------------------------------------------------
现状：
    失败只显示「失败N次」和原因，操作区无针对失败的快捷动作。
优化：
    - 当 warn_level==='error' 或 consecutive_failures>0 时，卡片浮一个红色「重试」按钮，
      调用 checkChaseTask 或新 retryChaseTask（重置 consecutive_failures 后重跑）。
收益：少翻历史、快速补救。  改动量：小。

--------------------------------------------------------------------------------
★5. 相对时间 + 下次检查倒计时（Sonarr Last aired / Next check）
--------------------------------------------------------------------------------
现状：
    写死 "2026/8/19 16:36 · 计划 DAILY:01:00"，对「是否还活着」不直观。
优化：
    - 最后成功时间显示为相对值："✅ 2分钟前"。
    - 下次检查显示倒计时："⏱ 下次约 8h 后（01:00）"。
    - 后端补 next_check 字段（由 schedule + last_check 推算），前端做相对化。
收益：立刻判断「是不是卡了」。  改动量：中（后端补 next_check）。

--------------------------------------------------------------------------------
★6. 缺失集可点击展开，支持单集手动触发（Sonarr 点 season 展开每集 grab）
--------------------------------------------------------------------------------
现状：
    整批追更，无法对单集补漏。
优化：
    - 卡片加「展开缺失集 ▾」，列出缺失集号，每集可单独「下载这一集」。
    - 复用现有 episodes_filter 机制，前端把选中集号写入该字段并触发检查。
收益：小范围精准补漏。  改动量：中（前端展开 + 单集触发接口）。

--------------------------------------------------------------------------------
★7. 批量操作条（Sonarr 列表顶部 Select all / Pause / Search）
--------------------------------------------------------------------------------
现状：
    「一键运行/一键停止」在列表外，无法对勾选子集操作。
优化：
    - 卡片支持勾选，顶部出现浮动批量条：「选中的 N 个 → 运行 / 停止 / 检查更新」。
收益：多任务管理效率提升明显。  改动量：中。

================================================================================
改动优先级
================================================================================
高（小改动高收益）：★1 进度条+缺失 / ★3 状态术语 / ★4 失败重试 / ★5 相对时间
中（需后端配合）：  ★2 三态分离 / ★6 单集展开 / ★7 批量条

逐条实施顺序：★1 → ★3 → ★4 → ★5 → ★2 → ★6 → ★7
（纯前端先做，需后端字段的后做；后端按需补 downloaded_eps / next_check）
